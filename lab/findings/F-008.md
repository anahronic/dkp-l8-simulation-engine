# F-008 — CRISIS allows extending oracle TTLs; ORACLE forbids it

**Status:** UNRESOLVED — contradiction between protocols (open question Q-027).
**Found by:** reading for the crisis module (S-LAB-06); kept as a regression in `tests/lab/test_findings.py`
(the quotes are checked verbatim in the pinned corpus).

## Texts

- DKP-4-CRISIS-001 §6 (Crisis Actions, allowed): "activate Crisis Mercy Mode for non-anthropogenic
  events (e.g., solar storms, geological phenomena), allowing limited extension of oracle data
  TTLs to prevent false system halts while preserving life-support continuity."
- DKP-0-ORACLE-001 §14 (Crisis Mercy Exception): the deferral of a Systemic Halt "DOES NOT modify
  TTL values, DOES NOT restore stale data weights, DOES NOT alter aggregation logic".
- DKP-0-ORACLE-001 §15 (Cross-Layer Isolation Invariant): "No higher-layer protocol may: … modify
  TTL values … Violation constitutes a **critical system integrity breach**."
- DKP-0-ORACLE-001 §17: the TTL registry is normative ("Maximum TTL").

CRISIS (L4) is a higher layer than ORACLE (L0).  The allowed action of CRISIS §6 is, by ORACLE
§15, a critical integrity breach; ORACLE §14 describes the same Mercy situation and keeps TTLs
unchanged — it defers the halt instead.

## Effect on a computation

With TTLs extended, stale data keep a weight: every check of ORACLE-9-01 (weight zero after TTL)
fails by construction during Mercy Mode, and dependent outputs are not degraded (compare
`failure_chain` with the deliberate fault `stale_weight_kept`).  With TTLs unchanged and the halt
deferred (ORACLE §14), the data lose weight but execution continues.
