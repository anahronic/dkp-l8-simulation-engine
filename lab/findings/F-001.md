# F-001 — A synchronous change of physical state triggers no re-evaluation

**Status:** UNRESOLVED — protocol/model gap; needs the author's decision. Not fixed in the lab.
**Found by:** module `failure_chain` (S-LAB-02), lab 0.1.0, corpus World `aad3e86`.
**Kept as regression:** example `value_drop_in_sync`; `tests/lab/test_failure_chain_module.py::test_value_drop_without_divergence_keeps_enforcement`; `tests/lab/test_findings.py`.

Three oracle classes read every hour; the true value falls from 100 to 80 at step 6;
enforcement applies above 90; 24 steps.  Variant `declared_events` uses the lab's reading

|---|---:|---:|---|---:|---:|

Under `declared_events` the asset restriction and the penalty accrual continue for 18
steps on evaluation EV-001 (value 100) while every admissible class reports 80.  **No
provision is reported as violated**: that is the gap.

## Chain of provisions (registry ids, verbatim quotes)

1. ORACLE §9, §10 — the readings are fresh and S(t) = 80 is computed correctly
   (ORACLE-9-01, ORACLE-9-02 PASS).
2. ORACLE §11 — "A Divergence Event is triggered when posterior distributions across
   independent oracle classes differ by more than **7%**."  All classes agree: no
   divergence, no freeze (ORACLE-11-01 PASS).
3. EB §5 — validity VALID, confidence SUFFICIENT_DATA, consistency CONSISTENT throughout.
4. ETRANS §4.1 — re-validation is triggered only by "VALID → CONDITIONAL / INVALID",
   "CONSISTENT → ORACLE_CONFLICT", "SUFFICIENT_DATA → DEGRADED_SIGNAL".  None occurs.
5. EB §3 / §7.1 — "**Dispute Event** Submission of new admissible data or conflict signal";
   the dispute triggers include "new admissible data".  A dispute is a submission; nobody
   submits one in this case.
6. ETRANS §4.2 (ETRANS-4.2-01) — "No enforcement output SHALL remain active solely based on
   past VALID state if: … new admissible data is introduced".  The text does not say whether
   routine readings are "introduced" new admissible data, nor how large a change must be.
7. ETRANS §3 item 4 (ETRANS-3-04) — "Re-evaluation is required for any state-dependent
   enforcement."  No timing or trigger is given.
8. EB §3 defines **Epistemic Drift** — "Mismatch between output and underlying physical state
   due to outdated or degraded inputs" — and **Stale Output** — "Output not revalidated under
   evolving conditions"; EB §9 says reliability degrades under "detected environmental
   change".  None of these definitions is attached to a state transition or a trigger.

The case is exactly the "epistemic drift" EB defines, reached without any listed trigger.

## Options for the author (none adopted; each would go through DKP-4-UPGRADE-001)

| Option | Text affected | Effect in the lab | Costs / open points |

| A. | C. Every evaluation carries a validity horizon (maximum age), after which `revalidation_required = TRUE` | EB §5 / §8, ETRANS §4 | not implemented yet | horizon per output type; may suspend enforcement while nothing changed |

Options A and D need a materiality threshold; B and C need none but change the cost and
the frequency of evaluations.  The lab can compare A and B now; C is not modelled.
